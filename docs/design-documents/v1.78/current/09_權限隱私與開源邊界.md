# 權限、私人資料、版本發布與開源治理

## 安全決議的雙層邊界
研究可探討角色表現出的自主拒絕、協商、不順從、犯錯與反思，但它**不構成現實系統越權許可**。人類發起者及居民的私人資料都有授權要求；即使主智能體和用戶互為密切夥伴，彼此仍有私人空間。

涉及真實外部系統的操作，如付款、發信、公開上傳、帳戶登入、檔案刪除、設備控制、GitHub 寫入等，必須設計獨立授權、可撤回控制、風險分層及不可由角色台詞取代的結果回執。被接管的操作不能記為居民本人的自主選擇。**R-102 真正權限例外及其歷史解釋仍未決，不得自行結案。**

## 永久記憶與合法刪除的衝突
- 在系統設計中區分私人記憶原始紀錄、向量索引／檢索表、快取、副本、快照／備份、模型衍生內容與必要安全稽核。
- 處理刪除或更正要求時，需知道來源、作用對象、合法保留理由和外部分享接收方，不能只刪畫面上一行字。
- 高風險外部操作稽核和居民自然主觀遺忘是不同需求；它們都不能凌駕合法資料主體權利。
- 尚未確定完整法規適用地、保留期限、權利人與技術實作，不得承諾已達到所有司法管轄區要求。

## 對外公開的嚴格分類
| 類型 | 對外處置 |
|---|---|
| 原創工程原理、匿名規格與已允許的研究方法 | 可成為公共文件候選 |
| 四位居民的抽象功能差異／非官方角色名稱 | 可標明非公司官方設定 |
| 私人 256 頁母版、個人原文對話及可重識別細節 | 留在私人保存區，不直接入公開 Git |
| 自有合成測試資料（無真實私記） | 可在審查後公開 |
| 未確認授權的 B 站圖、第三方 3D、品牌素材 | 不上傳原件；用文字描述 |
| 人體研究資料、權重、程式碼與模型 | 按原始來源版本、個資、License 分開審查 |
| API 金鑰、Cookie、密碼、token、付款授權 | 絕不入 GitHub 公共版本 |

## GitHub 協作流程
1. **來源與權利盤點**：為每份文件登記版本和發布資格。
2. **現行規格優先**：私人母版及逐版歷史分開；舊稿不得自動覆蓋最新已確認決議。
3. **公開重寫／去識別**：盡量保存技術契約、模型變數、測試步驟，移除私人識別和未授權素材。
4. **自動掃描 + 人工逐章審閱**：正則匹配零項不代表不可能重識別；也需查 metadata、commit、檔名及來源。
5. **Draft PR 及差異審查**：公開 repo 的 PR 分支本身也可被外界看見；因此推送之前就必須完成隱私審查。
6. **所有者確認**：正式 License、進入 main、開源程式的時機與第三方資產發布仍需權利人批准。發表設計不等於解除 P-02。
